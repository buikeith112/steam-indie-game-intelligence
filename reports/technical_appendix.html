Steam Indie Market Snapshot · technical appendix

How the dataset was built

Steam has no ready-made indie dataset. I pulled the raw API data into permanent, structured PostgreSQL tables, cleaned and validated it in Python and SQL, and modelled it for reporting. Every chart in the market snapshot is the output of a SQL query against those tables.

Row counts: live from the database, 13 Nov 2026Code: Python 3.12 · PostgreSQL 16

A.2Database schema

The core layer is built around one hub table, core.games, keyed on Steam's own app_id. Everything else joins to it.

Each line is a foreign key on app_id: one game (bar) to many rows (fork). Also in core, same pattern: review_histogram, reviews (sample), player_count_snapshots, news_events.

Why it is structured this way

  • Three layers. raw keeps the evidence, core is normalized so each fact is stored once, and mart is shaped for reporting. A parsing fix never needs new API calls, and reports never touch messy tables.
  • Steam's IDs are the keys. app_id is stable across all four APIs, so the same game from different sources lands in one row, and re-runs update rows instead of duplicating them.
  • Bridge tables for many-to-many. A game has many tags and companies. Developers and publishers share one companies table with the role on the bridge, which makes "self-published" a simple comparison.
  • History is keyed by game and date. Each daily run adds rows instead of overwriting yesterday. Prices change rarely, so they use SCD-2 (valid_from/valid_to), and a partial unique index allows only one current price per game.
  • Nothing is hard-deleted. Delisted games keep their row with a delisted_at date and stay in every rate, so failed games are not silently dropped from success rates (survivorship bias). One gap remains: Steam's catalog lists only games on sale today, so games removed before the first crawl were never captured, and older cohorts look somewhat better than they were.

A.3Cleaning, missing values and duplicates

ProblemHow it is handled
Mixed formatsRelease dates arrive as "12 Jan, 2024", "Q1 2025" or "Coming soon"; prices in cents; SteamSpy owners as "20,000 .. 50,000". Each is parsed into typed columns, keeping the raw string and a date_precision flag.
Inconsistent names"Devolver Digital, Inc." and "Devolver Digital™" become one company: strip ™®©, Unicode-normalize, case-fold, drop legal suffixes, then enforce a unique normalized name (54,444 companies).
Tags that aren't genres61 of 429 tags (Indie, Singleplayer, 2D…) are flagged is_meta and excluded from genre analysis.
Wrong price sourceThe batch API sometimes returned a bundle price (one game showed $44.98 for a two-game bundle). Bundle offers are now ignored, and a regression test covers it.
Missing valuesMissing stays NULL in storage, never 0: no review data is not the same as zero reviews. Queries decide case by case (see the note in A.4). SteamSpy hides data for some games, so 606 are marked "skip", not zero. Games with no usable price get an "unknown" bucket and are left out of price charts rather than imputed.
Sources that disagreeFour APIs fill different columns of the same row. Upserts use COALESCE(new, existing), so a source without a field cannot blank a value another source already filled.
DuplicatesSteam IDs as primary keys, plus composite keys such as (app_id, snapshot_date). Every write is either an upsert (INSERT … ON CONFLICT) or a delete-and-reinsert of one game's bridge rows, so re-running a game or a whole day updates rows instead of duplicating them.
Personal dataReviewer SteamIDs are SHA-256 hashed and review text is dropped before anything is stored, including in the raw layer.
 
-- Upsert into core.games: safe to re-run, and never overwrites a known value with NULL
INSERT INTO core.games (app_id, name, store_review_count, launch_date, ...)
VALUES (:app_id, :name, :store_review_count, :launch_date, ...)
ON CONFLICT (app_id) DO UPDATE SET
    store_review_count = COALESCE(EXCLUDED.store_review_count, core.games.store_review_count),
    launch_date        = COALESCE(EXCLUDED.launch_date,        core.games.launch_date),
    updated_at         = now();

Loading. Each game is loaded in one transaction per source: save the raw response, parse it, upsert the rows, mark its queue item done. If the process stops, at most one game is lost and the next run resumes from ops.ingestion_queue. Workers claim items with FOR UPDATE SKIP LOCKED, so three run in parallel (one per API host) without colliding. Schema changes ship as Alembic migrations.

A.4Two queries behind the charts

Hit rate by launch price (Question 3 chart)

-- Share of games reaching 1,000 reviews, by price bucket.
-- Launches 2018–2024, so every game has had ~2 years.
-- Delisted games are deliberately NOT filtered out.
SELECT b.price_bucket,
       count(*) AS games,
       avg((COALESCE(f.total_reviews, 0) >= 1000)::int)
           AS hit_rate,
       percentile_cont(0.5) WITHIN GROUP
           (ORDER BY COALESCE(f.total_reviews, 0))
           AS median_reviews
FROM mart.dim_game g
JOIN mart.fact_game_metrics f USING (app_id)
JOIN mart.dim_price_bucket  b
  ON b.price_bucket_id = g.price_bucket_id
WHERE g.launch_date BETWEEN DATE '2018-01-01'
                        AND DATE '2024-12-31'
GROUP BY b.price_bucket_id, b.price_bucket
ORDER BY b.price_bucket_id;

Why COALESCE(total_reviews, 0) here, when missing values stay NULL elsewhere? Steam's catalog returns a review count for every listed game, including an explicit 0. In this population none is missing: in the 13 Nov crawl, all 34,116 games launched 2018–2024 have a count, and 2,674 of them have zero reviews. So the COALESCE changes no result here. It is a guard for the denominator: if a count were ever missing, that game would stay in as "not a hit" rather than being dropped, which would quietly inflate the hit rate. A ratio is different. A game with no reviews has no positive share, so positive_ratio stays NULL and those games are left out of sentiment metrics. Games with no usable price (457 here) have no bucket and are excluded from this chart.

Share of games rated ≥80% positive, by genre (Question 2 chart)

-- bridge_game_tag = each game's top 5 genre tags.
-- is_very_positive_plus is defined once in fact_game_metrics:
--   total_reviews >= 50 AND positive / total >= 0.80
SELECT t.name                            AS tag,
       count(*)                          AS games,
       avg(f.is_very_positive_plus::int) AS share_80_plus
FROM mart.bridge_game_tag b
JOIN core.tags              t USING (tag_id)
JOIN mart.dim_game          g USING (app_id)
JOIN mart.fact_game_metrics f USING (app_id)
WHERE g.in_analytical_scope   -- 2018+, ≥10 reviews
  AND f.total_reviews >= 50   -- enough reviews to rate
GROUP BY t.name
HAVING count(*) >= 400        -- hide small genres
ORDER BY share_80_plus DESC;

A.5Refresh process: detecting new and changed records

The pipeline is incremental. steam-intel daily re-crawls the catalog (about 400 calls), compares it with what is stored, and re-queues only the per-game work that is due. scripts/register_daily_task.ps1 schedules it as a 03:00 Windows task.

ChangeHow it is detectedWhere it lands
New gameAn app_id in today's crawl that is not in core.gamesInserted, then queued for per-game collection
Removed gameNot seen in today's crawl (last_seen_in_catalog_at is older than the run), then confirmed against its store pagedelisted_at set; the row is kept
Price changeToday's price compared with the game's open price_history rowOld row closed, new version opened (SCD-2)
Review growthReview count captured for every game on every crawlOne catalog_snapshots row per game per day
Metadata driftStore details fetched for new games immediately, then re-fetched on a rotation (1/30 of games per day)Upserted into core.games and its bridges
Early-review window closesA game turns 30 or 365 days oldreview_windows row recomputed and marked complete
 
-- Price change (SCD-2). Python compares the new price with the open row
-- and runs this only if it differs.
-- 1. Close the current version
UPDATE core.price_history SET valid_to = :observed_at
 WHERE app_id = :app_id AND valid_to IS NULL;
-- 2. Open the new version
INSERT INTO core.price_history
       (app_id, valid_from, initial_cents, final_cents, discount_pct, source)
VALUES (:app_id, :observed_at, :initial_cents, :final_cents, :discount_pct, :source);

-- Guardrail in the schema: at most one current price per game
CREATE UNIQUE INDEX ux_price_open ON core.price_history (app_id)
 WHERE valid_to IS NULL;

After loading, the run refreshes the materialized views with REFRESH MATERIALIZED VIEW CONCURRENTLY, so reports stay readable during the reload. It then recomputes the statistics, runs the data-quality checks, and logs the outcome to ops.ingestion_runs. Price history is already recording versions: for 5 games, the store-page API reported a different price than the batch API, so each has two rows with the source stored on each.

The two coverage checks gate any result that depends on per-game data. That is why the market snapshot covers only questions answerable from the full catalog crawl.

Other checks

  • Completeness. The first crawl returned 60,230 games. Re-querying with each sort order showed that the default ordering shifts while paging. A stable sort returned 65,471, and the crawl now warns if coverage drops below 99.5%. Both runs are logged in ops.ingestion_runs.
  • Automated tests (51). They cover parsers against recorded real API responses, and retry and backoff against simulated 429, 403 and 500 errors. One test loads data end to end (catalog → workers → marts → checks) into a throwaway PostgreSQL.
  • Cross-source reconciliation. Per-game review totals were compared with the catalog's totals for the same games. Paid games agreed (median ratio 1.00). All 2,427 free games collected so far came back far too low (Splitgate: 165 against 110,314). The cause: the per-game call counted only "Steam purchases", and free games have none. Free games now count all reviews, matching the store page, and the 2,460 affected games were re-queued. The snapshot was unaffected, because it was computed from the catalog totals.
  • Spot checks. Stored review totals, prices and tags were compared with live store pages for well-known games. This is how the bundle-price bug was found.
  • Analysis guardrails. Segments with fewer than 30 games are hidden, and regressions require at least 200 games.
  • Privacy audit. A query confirms that 0 stored review payloads contain a raw SteamID or review text.
